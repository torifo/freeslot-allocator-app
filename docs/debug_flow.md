# デバッグフロー

このドキュメントは、UI修正と機能修正を進める前提の実務フローをまとめたものです。`must` の不具合を先に潰し、その後にモバイル向けの操作性を詰めます。

## 1. 事前確認

最初に次を実行します。

```bash
flutter analyze
flutter test
```

失敗した場合は、UI調整より先に原因を特定します。

## 2. 対象機能を固定する

一度に広く触らず、次の単位で区切ります。

1. `task_master`
2. `daily_plan`
3. `weekly_report`

不具合が複数ある場合でも、1つの導線を最後まで再現してから修正します。

## 3. 再現手順を残す

不具合や違和感を見つけたら、最低限これを残します。

- 画面
- 操作手順
- 期待結果
- 実際の結果
- 再現条件

例:

- 画面: `DailyPlan`
- 手順: slot A の予定を slot B にドラッグ
- 期待: 枠内に収まる場合だけ移動
- 実際: 重複した枠でも保存できる

## 4. 修正順

優先度は次の順です。

1. データ破損や誤集計
2. 保存できない / 操作できない不具合
3. モバイルでの導線不良
4. 文言や見た目の微調整

レビューコメントのラベルは次を使います。

- `must`
- `ask`
- `good`
- `imo`
- `nits`
- `fyi`

## 5. 修正後の確認

修正後は、対象導線の手動確認に加えて次を実行します。

```bash
flutter analyze
flutter test
```

必要ならエミュレータで縦長端末と小さめ画面の両方を確認します。

## 6. コミット方針

- 修正内容は小さく分割する
- 機能修正とテスト追加は分ける
- コミットメッセージは英語 / 日本語併記にする
- 機能追加や修正では本文で詳細を補足する
