# Flutter開発フロー

この要点定義書をそのまま実装に落とす前提で、**Flutterの開発フロー**を「何から決めて、どの順番で作るか」に絞ってまとめる。

プロジェクト敬称は **Frelocator（フリロケーター）** とする。

Flutter未経験のフルスタック開発者向けには、実作業の入口を補うガイドとして [flutter_onboarding_for_fullstack_developer.md](/Users/akito-shoji/dev/app/frelocator/docs/flutter_onboarding_for_fullstack_developer.md) も参照すること。

## 補足: プロジェクト名とリポジトリ名

- プロジェクト敬称は **Frelocator（フリロケーター）** とする。
- フォルダ名は `frelocator` とする。
- リポジトリ名は `freeslot-allocator-app` とする。
- 日本語名は未決定とする。
- このプロジェクトフォルダ配下に `app` という名前のフォルダを作る予定はない。

今回のアプリは、**日付・時間枠・タスク割り当て・週次集計**が中心なので、Flutter公式の推奨どおり、最初に**アーキテクチャとデータ責務を分けて**進めるのが重要である。Flutter公式でも、拡張しやすく保守しやすい構成として、UI・状態管理・データ層を分離する進め方が案内されている。加えて、複雑な永続データにはSQL系の採用が適しているとされている。([Flutterドキュメント][1])

## 全体の進め方

このアプリのFlutter開発フローは、次の順で進めると詰まりにくい。

1. **要件をMVPに絞る**
2. **画面一覧と遷移を決める**
3. **データモデルを確定する**
4. **ローカル保存方式を決める**
5. **アーキテクチャを切る**
6. **画面を仮組みする**
7. **CRUDを先に完成させる**
8. **時間割り当てロジックを作る**
9. **週間レポートを実装する**
10. **テスト・調整・将来拡張の整理をする**

## 1. まずMVPを固定する

要点定義書の内容から、最初に作るべきMVPはかなり明確である。

MVPに入れるものはこの9個で十分である。

- 日付ごとの自由時間枠作成
- タスクマスター管理
- タスクの1分単位割り当て
- 日またぎ対応
- 過去プランの複製
- 日付一覧
- 日別詳細
- 週間レポート
- ローカル保存

逆に、通知・Googleカレンダー連携・クラウド同期・AI提案は後回しでよい。Flutter公式も、アプリをスケールさせる前提でも、最初から全部盛りにせず、責務を分けて増やせる構造にする考え方を勧めている。([Flutterドキュメント][1])

## 2. 次に画面遷移を決める

このアプリは、先に機能より**画面の主導線**を固めた方が作りやすい。

基本導線は次のとおり。

**ホーム（日付一覧）**
→ **1日詳細**
→ **自由時間枠編集**
→ **タスク割り当て**
→ **タスク一覧 / タスク編集**
→ **週間レポート**

この順にすると、ユーザー体験も自然になる。

### 画面ごとの役割

**ホーム / 日付一覧**

- 今日・未来日の計画状況を見る
- その日の詳細へ入る

**1日詳細**

- 自由時間枠一覧
- 枠ごとの割り当て済みタスク
- 複製、追加、編集

**自由時間枠編集**

- 開始・終了日時
- 日またぎ
- メモ

**タスク一覧 / 編集**

- タスクマスターの追加編集
- 絞り込み
- 優先度確認

**タスク割り当て**

- どのタスクをその枠に入れるか決める
- 開始・終了を1分単位で設定
- 並び替え

**週間レポート**

- 円グラフ
- 合計時間
- 割合
- 件数
- 週切り替え

この段階では、まだ細かいデザインより、**画面間の責務の重複をなくす**ことが大事である。

## 3. データモデルを確定する

今回のアプリは、Flutterで先にUIを作るより、**データ構造を先に固めた方が速い**。理由は、週次集計や複製機能がデータ設計に強く依存するからである。

定義書のモデルはそのままベースにして問題ない。

### 中核になる関係

- **TaskMaster**: 割り当て元の原本タスク
- **DailyPlan**: 1日単位の計画
- **FreeTimeSlot**: その日の自由時間枠
- **SlotTaskAssignment**: 各枠に置かれた実際の予定

この4層で考えると整理しやすい。

### 実装上の重要ポイント

**SlotTaskAssignment を独立させているのが重要**である。これにより、次がやりやすくなる。

- その日だけタイトル変更
- その日だけ時間微調整
- 過去プラン複製
- 週次集計

### カテゴリ設計で先に決めること

カテゴリは固定マスターではなく、**初期値ありのユーザー編集可能データ**として扱う方がよい。

- 初期カテゴリは用意してよい
- ユーザーが追加・編集・削除できる
- 変更内容はローカル保存する
- `やるべきこと` と `やりたいこと` はカテゴリ体系を共有するかをユーザーが切り替えられるようにする

共有をONにする際、両者のカテゴリ内容が一致していない場合は、その場で統合方針を選ばせるのが安全である。

- 少ない方に合わせる
- 多い方に合わせる
- `やりたいこと` 側に合わせる
- `やるべきこと` 側に合わせる

この仕様は後から足すと、TaskMaster保存形式と週次集計ロジックの両方に影響する。そのため、MVP段階でデータモデルに入れておくべきである。

## 4. 保存方式を決める

今回のアプリは**ローカル保存が前提**で、しかもデータ同士の関係が多い。そのため、単純なキー値保存より、**SQL系ローカルDB**の方が相性が良い。Flutter公式でも、複雑な永続データにはSQLアプローチを案内している。([Flutterドキュメント][2])

### おすすめ

**drift + sqlite**

- リレーションを扱いやすい
- 集計しやすい
- 日付範囲検索しやすい
- 週間レポート実装に向く

### 軽量寄りの代替

**Hive CE**

- 軽い
- オフライン向き
- 開発開始は速い

ただし、今回のような「日付横断集計」「関連データ参照」「週次レポート」では、後から検索や集計が少し苦しくなりやすい。Hive CE自体はFlutter向けのローカル保存手段として機能や開発支援を備えている。([Dart packages][3])

そのため今回の要件なら、実務的には**drift優先**が無難である。特に週間レポートがあるので、最初からSQL寄りにしておく方が安全である。これは公式のSQL永続化ガイドの方向性とも合っている。([Flutterドキュメント][2])

## 5. アーキテクチャを切る

Flutter公式は、UIとデータ処理を分離した構成を推奨している。状態管理についても、アプリ規模やチーム方針に応じて外部パッケージを使う選択肢を示している。([Flutterドキュメント][1])

このアプリなら、次のように切ると分かりやすい。

### 推奨構成

- **presentation**: 画面、Widget、表示用状態
- **application**: ユースケース、集計、複製、割り当てロジック
- **domain**: エンティティ、値オブジェクト、ルール
- **data**: DB、repository実装、DTO

### 状態管理

実装しやすさ重視なら、**Riverpod** か **Provider系** が相性良い。Flutter公式も、状態管理は標準だけでなくコミュニティ製パッケージの利用を前提に案内している。([Flutterドキュメント][4])

今回の規模なら、次の組み合わせが扱いやすい。

- **Riverpod**
- **go_router**
- **drift**
- **freezed / json_serializable は必要に応じて**
- **fl_chart** で円グラフ

pub.devにはチャート系パッケージ群があり、週次可視化の実装候補を選べる。([Dart packages][5])

## 7. 画面は「見た目だけ」先に仮組みする

ここでいきなりDB接続しない方が良い。最初はモックデータで、以下だけ確認する。

- 日付一覧の見え方
- 1日詳細のレイアウト
- 自由時間枠の表示
- タスク割り当てUI
- 週間レポート画面の情報量

この段階の目的は、**使いにくいUIを早く見つけること**である。

今回だと特に見るべきポイントは次のとおり。

### 先に検証すべきUIポイント

- 1分単位入力をどうさせるか
  → 時刻ピッカーだけで足りるか
- 日またぎ枠をどう見せるか
  → 4/17 23:30〜4/18 00:20 の視認性
- タスクを時系列で編集しやすいか
- 円グラフと数値一覧のバランス

## 8. その後にDBとCRUDを入れる

UIの骨組みが見えたら、次に**作成・一覧・更新・削除**を通す。

実装順は次がおすすめである。

### 実装順

1. TaskMaster CRUD
2. DailyPlan 作成・取得
3. FreeTimeSlot CRUD
4. SlotTaskAssignment CRUD
5. DailyPlan 複製
6. WeeklyReport 集計

この順なら、後ろの機能ほど前の機能を使い回せる。

## 9. 一番大事なのは時間割り当てロジック

このアプリの本体はここである。単にデータを保存するだけではなく、**自由時間枠に対して矛盾なく予定を置けること**が価値になる。

### 実装すべきルール

- 開始 < 終了
- 1分単位
- slotの範囲内に収まるか
- タスク同士が重複していないか
- sortOrderと時系列が矛盾していないか
- 日またぎでも正しく計算できるか

### 例

自由時間枠
4/17 21:00〜24:30

割り当て

- 21:00〜21:18
- 21:18〜22:02
- 22:02〜22:47

このとき、次をアプリ側で判定する。

- 連続しているか
- 途中に空き時間があるか
- 枠超過していないか

ここは**UIで防ぐ**のと**保存時に再検証する**のを両方やるべきである。

## 10. 過去プラン複製は早めに作る

このアプリの差別化ポイントの1つなので、後回しにしすぎない方が良い。

複製機能は大きく3種類ある。

- 1日まるごと複製
- 自由時間枠だけ複製
- タスク構成を編集して再利用

### 複製時の実装方針

- DailyPlanを新規作成
- FreeTimeSlotをコピー
- SlotTaskAssignmentをコピー
- TaskMasterは原本参照のままでもよい
- customTitle / customMemo は引き継ぎ可
- 日時だけ新しい日付へ合わせて再計算

## 11. 週間レポートは最後ではなく、設計だけ先に決める

実装は後でもよいが、**集計仕様は先に決める**べきである。理由は、後から「件数」「割合」「カテゴリ別」が必要になると、保存形式やクエリが変わるからである。

### 週次集計で持つべき観点

- カテゴリ別合計分数
- やるべきこと / やりたいこと別合計分数
- 端末別合計分数
- 件数
- 合計時間
- 割合

### 円グラフで表示するもの

- カテゴリ別
- やるべき / やりたい
- 端末別

### 補足

円グラフだけだと比較しづらいことがあるので、**円グラフ + 数値一覧**が実用的である。チャートの実装候補はpub.dev上で選べる。([Dart packages][5])

カテゴリ共有設定がOFFのときは、`やるべきこと` と `やりたいこと` のカテゴリ別集計を分けて扱えるようにしておく。共有設定がONのときは共通カテゴリ軸で集計する。この切り替え前提があるため、集計クエリも共有ON/OFFを前提に設計した方がよい。

## 12. テストはどこを重点的にやるか

このアプリは、見た目よりも**時間計算の不具合**が怖い。そのため、Widgetテストよりまずロジックテストを厚くする。

### 優先してテストする箇所

- 日またぎ時間計算
- 1分単位丸め
- 枠超過判定
- 重複判定
- 複製後の日時変換
- 週間集計結果

### テストの考え方

- UIテストは薄めでもよい
- domain / application 層は厚めに
- repositoryは最低限の動作確認
- 手動確認で時刻入力UXを見る

## 14. 今回のアプリにおすすめの技術選定

MVPを堅く作るなら、次の組み合わせを勧める。

- **Flutter**
- **Riverpod**
- **go_router**
- **drift + sqlite**
- **fl_chart**
- **intl**
- 必要なら **freezed**

理由は次のとおり。

- ローカル中心
- データ関連が複雑
- 週次集計がある
- 将来Googleカレンダー連携も足しやすい

Flutter公式のアーキテクチャ方針とSQL永続化の考え方にも合っている。([Flutterドキュメント][1])

## 15. 一言でいうと、Flutter開発フローはこうなる

このアプリでは、

**要件整理 → 画面遷移確定 → データ設計 → ローカルDB設計 → 状態管理導入 → 画面仮組み → CRUD実装 → 時間割り当てロジック実装 → 週間レポート実装 → テスト**

の順が一番きれいである。

特に重要なのは、**「UIから作り始めすぎないこと」** と **「週間レポートを見越して最初からDB設計すること」** である。

次に進めるなら、要点定義書をもとに **Flutter向けの「画面一覧 + 状態遷移 + データ設計書」** まで具体化する。
